# Kodama 設計書

> **Kodama（木霊）**：プレイヤーの動きに応じて世界が「こだま」のように応える、適応型Minecraftサーバーソフトウェア。
> Leaf・Gale・Purpur など植物／自然系の命名の流れも汲んでいる。

---

## 0. 基本方針

| 項目 | 決定内容 |
|---|---|
| ベース | **Paper**。Leafから有用なパッチのみ選択的に取り込む |
| 互換性 | **Spigot / Paper プラグイン完全互換**が必須目標 |
| 言語 | Java（言語変更はしない。重さの原因は言語でなく処理構造） |
| 並列化方針 | Bukkit APIはメインスレッド前提のため、プラグインから見える順序・挙動は変えない |
| 除外するもの | Foliaのようなリージョン並列化、Leafの並列ワールドtick等の実験機能 |
| 設計思想 | 「プラグインが触ったら従来処理に戻す」を全機能共通の互換原則とする |

### 0.1 Leafパッチ取り込みルール
- 元のパッチ単位でそのまま取り込む（書き直さない）→ Leaf更新時に差分を追いやすくする
- パッチヘッダに出典を明記。上流ライセンスが混在しているため、パッチごとに元ライセンスを確認
- 優先候補：非同期経路探索、非同期Mobスポーン、エンティティトラッカー非同期化、不要パケット削減
- 取らないもの：並列ワールドtick等の実験系
- 独自機能はLeaf固有コードへの依存を最小化し、機能単位でパッチ分離＋設定でON/OFF可能にする

## 1. Mob LOD（距離別AI段階制御）

### 1.1 ティア定義
距離判定は**一番近いプレイヤーとの座標距離のみ**（視線方向は使わない）。

| ティア | 処理内容 |
|---|---|
| 遠距離 | **座標シミュレーションのみ**。x/y/z・向き・移動ベクトルを保持し、数tickに1回ランダム方向へ移動。AI・経路探索・当たり判定・重力計算はスキップ。y座標はハイトマップ参照で地表に貼り付け |
| 中距離 | AIは主要ゴールのみ・経路探索は低頻度＋キャッシュ。**物理（重力・水流・ブロック衝突）は完全バニラ** |
| 近距離 | 完全バニラ |

- ティア境界はヒステリシス付き（入る距離と出る距離をずらす）
- 遠距離Mobは**数値配列（SoA）で一括保持**し、Vector APIによるSIMD／並列一括更新を行う
- 処理を軽くすることで、エンティティ追跡範囲を広げ「遠くにMobが見えない」問題も解消する
- 遠距離Mobの移動パケットは送信頻度を下げる（クライアント補間に任せる）

### 1.2 昇格（復元）処理
- 遠→中へ上がる際、座標が壁・水中・崖でないか1回検証して補正し、完全状態に復元
- 急接近（エリトラ等）によるスパイクを避けるため、**復元は数tickに分散**

### 1.3 プラグイン互換：「触ったら即昇格」
- AI系API（`getTarget()`、`getPathfinder()`、`setAI()`、Goal操作等）が呼ばれたら、そのMobを即座に完全状態へ復元してから値を返す
- 座標・体力・名前など単純データはそのまま返す
- 昇格後は一定時間（例：数十秒）遠距離ティアに戻さない

### 1.4 常に対象外とするMob
- カスタムGoal登録済み、メタデータ／PDC保持（MythicMobs・Citizens系を想定）
- 名前付き・リード付き・騎乗中・ターゲット保持中・ボス系

### 1.5 湧き上限（mob cap）
- **遠距離ティアのMobも通常通りカウント**（バニラと同じ）
- 湧き判定・上限計算ロジックには一切手を入れない
- 遠距離ティアでも種類・カテゴリ・位置は常に保持

### 1.6 デスポーン判定
- バニラ準拠（128ブロック超で即消滅、32〜128で確率消滅、永続フラグは消えない）
- 遠距離ティアでNtickまとめて処理する場合、**確率をNtick分に換算**して判定（統計的にバニラ一致）
- 無行動カウンタもまとめた分を加算
- 永続フラグ・無行動カウンタは遠距離ティアでも常に保持
- 128ブロック即消滅が処理間隔分遅れるのは許容

### 1.7 トラップタワー保護
1. **待機プレイヤー検出**：一定時間（例：3分）ほぼ動かないプレイヤーの周囲128ブロックは遠距離ティアにしない
2. **環境検出**：水流中・足場が空中・落下中のMobは自動で中距離以上へ昇格
3. **手動指定**：管理者がコマンド／設定で「LOD無効範囲」を指定可能

## 2. チャンク読み込み

### 2.1 予測プリフェッチ
- 速度ベクトルから数秒後の位置を予測して先読み
- 先読み距離は速度比例（徒歩＝ほぼ無し、エリトラ＝遠方まで）
- 形状は進行方向に伸びた**扇形**
- エンダーパールは投擲時に弾道計算し、着地点を先読み

### 2.2 優先度キュー
- スコア＝距離＋進行方向とのズレ角（正面優先、背後は後回し）
- **既存チャンク読み込みと新規生成を別キューに分離**（生成待ちで既存送信が詰まるのを防止）
- 背後チャンクはアンロードを遅延（Uターン対策）

### 2.3 送信パケットキャッシュ
- シリアライズ＋圧縮済みバイト列をチャンク単位で保持、ブロック変更でダーティ化
- ProtocolLib等でチャンクパケットをプレイヤーごとに書き換えるプラグインがいる場合、そのプレイヤー分はキャッシュを使わず従来処理
- 上限サイズ付き

### 2.4 生成の高速化
- ノイズ計算をVector APIでSIMD化（**バニラと1ブロックも違わないこと**が前提）
- 生成スレッド数を動的制御（アイドル時は増、TPS低下時は減）
- GPUは使わない（浮動小数誤差による地形ズレ、データパック／ChunkGeneratorとの非互換、転送コスト）

### 2.5 バックグラウンド・プリキャッシュ（事前生成の内蔵）
- 起点：**スポーン地点＋プレイヤーがよく行く方向**（移動履歴ヒートマップ）。複数人なら各自の周辺を均等に
- 負荷制御：MSPTが閾値（例：35ms）超で即停止、プレイヤー由来の要求を常に優先、オンライン0人時は全力
- 生成後すぐ保存＆アンロード（メモリに抱えない）
- 上限半径・ディスク使用量上限を設定可能。ワールドボーダーがあればそれを上限に
- 進捗を保存し、再起動後に続きから再開
- `ChunkLoadEvent`（新規チャンク）はデフォルトで発火（構造物カスタム系プラグインのため）。設定で抑制可能

### 2.6 プレイヤー行動適応
直近数分のスライディングウィンドウで以下を計測：
- 新規チャンク踏破数／分、平均速度、エリトラ・乗り物使用、行動範囲の広さ

| タイプ | 特徴 | チャンク処理 |
|---|---|---|
| 定住型 | 拠点周辺で建築・採掘 | 先読み最小、周辺を長めに保持、アンロード遅延長め |
| 移動型 | 拠点間を往復 | 既知ルート上を先読み |
| 探索型 | 未開拓地を飛び回る | 扇形先読み最大、プリキャッシュ起点をこの人の進行方向へ |

- 過去傾向を初期値に、当日の実測で随時上書き（ヒステリシス付き）
- サーバー全体のチャンク処理予算に上限を設け、**全員に最低保証枠**を確保した上で余りを探索型へ配分
- 行動データはプレイヤーデータに数値数個を追加するのみ

## 3. 赤石・ホッパー

### 3.1 装置の自動分類（チャンク単位で更新を記録）
| 分類 | 判定材料 | 扱い |
|---|---|---|
| 一時型 | 起点がボタン・レバー・感圧板・トリップワイヤー、更新が一瞬で収束 | VANILLAのまま触らない |
| 常時型 | 一定周期の繰り返し（クロック）、起点がオブザーバー・日照センサー等、一定時間内の発火回数が多い | 最適化・通知の対象 |
| 異常常時型 | 極端に短い周期で負荷突出 | ラグマシン候補として警告（対策は管理者判断） |

### 3.2 赤石実装のチャンク単位切替
- デフォルトは全チャンクVANILLA
- 重い常時型チャンクを検出したら**管理者に通知のみ**（自動切替はしない）
- 管理者／チャンク所有者がコマンド・GUIで「このチャンクはAlternate Current」と指定。チャンクに保存し再起動後も維持
- 切替はそのチャンクの赤石が静かなタイミングで行う

### 3.3 ホッパー
- **移動イベント自動スキップ**：`InventoryMoveItemEvent` のリスナーが無いときだけ発火を省略。登録されていれば従来通り
- **アイドル休眠**：空・満杯・転送先なしのホッパーはポーリングせず、インベントリ変化／赤石更新で起こす
  - 時間あたり転送数がバニラと一致しない場合は不採用

## 4. ネットワーク

- **プレイヤー別の動的圧縮**：RTT・送信キューの詰まり具合から圧縮レベル／閾値を自動調整
- **Mob LOD連動**：遠距離ティアのMobは移動パケット頻度を下げる
- **無駄な更新の抑制**：誤差レベルの座標・向き変化は送らない（Leafの同系パッチを取り込み候補に）
- **帯域枠分け**：1プレイヤーの送信をチャンク用とそれ以外で分け、探索型がエンティティ更新を圧迫しないようにする

---

## 5. メモリ / GC

- **JVM推奨設定を起動スクリプトに同梱**
  - Compact Object Headers：デフォルトON
  - GC：調整済みG1と世代別ZGCの2択を同梱し、ベンチで決定
- **割り当て削減**：衝突判定・経路探索・チャンク処理のホットパスで一時オブジェクトを再利用
- **遠距離Mobは数値配列で保持**（GC対象削減＋SIMD化）
- **独自キャッシュは全て上限サイズ付き**（ヒープの◯%まで等）

## 6. 設定

### 6.1 ファイル構成
- `config/kodama-global.yml`：サーバー全体（プリキャッシュ、ネットワーク、メモリ関連）
- `config/kodama-world-defaults.yml`：ワールド共通既定値（Mob LOD、赤石、ホッパー）
- ワールドごとの上書き可能
- 全機能に `enabled`、各機能に互換モード／積極モード

### 6.2 プリセット
| プリセット | 内容 |
|---|---|
| `safe` | バニラ挙動を一切変えない最適化のみ |
| `balanced`（デフォルト） | 本設計書の内容 |
| `aggressive` | 統計一致を多少犠牲にしても軽さ優先 |

プリセット選択後に個別項目を上書き可能。

### 6.3 ホットリロード
| 分類 | 例 | 反映方法 |
|---|---|---|
| 即時反映 | 距離閾値、通知ON/OFF | tick境目で差し替え |
| 段階反映 | Mob LOD、チャンクキャッシュ、赤石実装 | 数tickに分散して移行 |
| 再起動必須 | GC、ヒープ、Compact Object Headers | reload時に「再起動まで未反映」と表示 |

- 新設定は**検証してから反映**。不正なら旧設定を維持してエラー表示

### 6.4 ゲーム内設定
**コマンド**
- `/kodama config set <項目> <値>` / `get <項目>`（タブ補完・範囲チェック付き）
- `/kodama config undo`：直前の変更を戻す
- `/kodama status`：機能ON/OFF、Mobティア別数、プレイヤータイプ判定、プリキャッシュ進捗
- `/kodama reload`

**インベントリGUI**（`/kodama gui`）
- トップ：カテゴリ（Mob LOD、チャンク、赤石、ネットワーク…）
- ON/OFF：クリックで切替（緑／赤の羊毛等）
- 数値：左クリック＋、右クリック−、シフトで大きく増減
- 選択肢：クリックで順送り
- 説明文に現在値・既定値・反映タイミングを表示
- 「今いるチャンク」に赤石実装を適用するボタン

**共通ルール**
- 権限は閲覧／変更で分離、項目ごとに権限ノード
- YAML書き戻し時にコメントを保持
- 変更履歴（誰が・いつ・何を）をログ記録
- 同時編集は後勝ち＋相手に通知
- 統合版（Geyser経由）でのGUI動作もテスト対象

### 6.5 安全装置
- 独自機能で例外が連発したら、**その機能だけ自動無効化＋警告ログ**。サーバー全体は落とさない

## 7. 計測・ベンチ基盤

### 7.1 構成
- 固定シード＋事前生成済みテストワールド
- ボット：Mineflayer（経路探索プラグインは使わず、座標指定の単純移動スクリプト）。1プロセスに集約
- 行動パターン：定住型／探索型（エリトラ直進）／混合を人数指定で再現
- 素のPaper vs Kodama を同条件で自動比較・レポート化、CIで性能退行を検知

### 7.2 計測項目
- MSPT（平均・p99）
- チャンク到達遅延
- メモリ・GC停止時間・割り当て量／tick
- 送信帯域
- トラップタワー効率（時間あたりドロップ数）

### 7.3 実行環境（Ryzen 5 5600 / 32GB / RTX 5060）
| 用途 | 割り当て |
|---|---|
| サーバー | 4コア8スレッド固定（CPUアフィニティ）、ヒープ10GB |
| ボット | 2コア4スレッド |

- 普段（パッチごと）：10体・短時間
- 定期（週1）：50体・長時間
- GPUは本設計では使用しない

## 8. バニラ一致テスト

| 対象 | 方法 | 合格基準 |
|---|---|---|
| チャンク生成 | 複数シード（5〜10）×オーバーワールド・ネザー・エンドで半径100チャンク生成し比較 | ブロック・バイオーム・構造物が**完全一致** |
| Mob LOD | Mob総数・種類分布・デスポーン数を比較 | 許容範囲内の統計一致、近距離ティアは挙動完全一致 |
| トラップタワー | 湧き層＋落下式で効率比較 | 時間あたりドロップ数一致 |
| ホッパー休眠 | 時間あたり転送数を比較 | 一致（不一致なら機能不採用） |
| プラグイン互換 | EssentialsX、WorldEdit、LuckPerms、ProtocolLib、MythicMobs等でスモークテスト | 「触ったら即昇格」「ProtocolLib検出でキャッシュ無効」が機能すること |

実行タイミング：生成系変更時＋週1、統計・プラグインは定期ベンチと同時。
